# Existing proxies and other networks

[Back to the guide](../README.md)

## Already using Caddy

You do not need to replace a working Caddy installation. If browsers already publish and view through it, first address the native VDO.Ninja app's certificate trust.

With `tls internal`, Caddy creates its own CA and manages server certificates. Keep its data directory persistent. Export **the public root certificate**, usually `pki/authorities/local/root.crt` relative to Caddy's data directory. The data directory depends on your installation; in a standard container it is commonly under `/data/caddy`. Never share `root.key` or export the whole CA directory to clients.

Trust that root on clients. The app needs support for this same root; a second CA generated by this repository will not validate Caddy's certificate. Caddy's internal server certificates are short-lived (12 hours by default), so trusting each individual leaf certificate is inconvenient. See [Caddy local HTTPS](https://caddyserver.com/docs/automatic-https#local-https) and [its internal issuer](https://caddyserver.com/docs/caddyfile/directives/tls#internal).

There are **two connections** to configure if Caddy proxies to this package:

1. Device → Caddy: the device trusts Caddy's certificate, at the external port, e.g. 443.
2. Caddy → Node: this repository's Node server also uses HTTPS. Configure Caddy's upstream trust and expected certificate name accordingly, using a name/IP covered by the backend certificate. Plain `http://` to the Node HTTPS port will fail.

Do not solve the second connection by disabling TLS verification. Caddy's [reverse-proxy transport documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#the-http-transport) describes configuring upstream TLS trust. This guide does not add a plain-HTTP backend or require a proxy.

## A VPS or devices on different networks

The certificate concepts transfer, but the LAN configuration is not a complete VPS deployment. Public hosting adds firewall/access control, abuse prevention and peer-to-peer reachability requirements. A public hostname with a publicly trusted certificate can avoid installing a private root, but obtaining/renewing that certificate normally requires connectivity to the issuer.

This guide sets `session.configuration = {}` in its deployment copy to avoid public STUN/TURN services. Across NATs, subnets, isolated Wi-Fi or the internet, you may need your own STUN/TURN configuration. The HTTPS signaling port does not relay media or automatically open the paths media needs. Review [VDO.Ninja self-hosting documentation](https://github.com/steveseguin/vdo.ninja/blob/master/install.md) before adapting this LAN recipe.

## Offline WHIP/WHEP

For a separate WHIP/WHEP service, see [steveseguin/whip](https://github.com/steveseguin/whip). This repository supplies the VDO.Ninja website and routed WebSocket signaling; it does not install that service. Give each HTTPS endpoint a certificate covering its actual hostname/IP, including every name when sharing a certificate.

## Existing vanilla installations

The Node server preserves the old defaults: `PORT=443`, key `./key.pem`, certificate `./cert.pem`, and the sibling `../vdo.ninja` website directory. Those key paths remain relative to the process working directory. New installations use explicit absolute paths and port 8443 instead.

You can set `WEB_ROOT` to your prepared website folder without moving it. Keep certificates and backups outside that folder. Do not point it at this entire repository. No changes to existing sibling checkouts are needed to use the new guide.

The signaling protocol **has changed** to advanced routing. Existing deployments must update their local website configuration to `customWSS = false` and replace browser `wss` overrides with `wss2` when adopting this server. See [migration instructions](maintenance.md#update-the-website). The file-path defaults above do not imply compatibility with the old fanout wire protocol.
